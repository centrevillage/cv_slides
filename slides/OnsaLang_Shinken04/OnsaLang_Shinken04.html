DSPプログラム言語「Onsa」

~おれの理想のプログラム言語編~

centrevillage Shinken #04 2026-10-14

なぜ新しい言語を作るのか？

  • LLM が書きやすい言語とは？
    • 読みの別れない一貫した文法
    • 同形同義・異義異形の原則、表現の一意性
    • エラーが局所的で関数の中に閉じるので修正ループを高速に回せる
  • 今、新しい言語が必要だとしたら、どの領域？
    • 汎用言語は飽和。LLM は既存の言語を十分に書ける
    • LLMの事前知識にない新言語は不利
  • DSP(音の信号処理)なら？
    • 定番の FAUST は強力だが、記法が独特で LLM も人も読みづらい
    • FAUST の代わりになる言語なら、作る価値があるかも？

何がしたいのか

  • LLM を使って開発を高速化したい
    • エフェクターやシンセの「中身」を、言葉で指示して書かせる
  • IDE で音を確かめながら開発したい
    • FAUST のように、書いたそばから鳴らして聴く
  • あらゆる環境にトランスパイルできる「基準」にしたい
    • PC のプラグインも、ヒープのないマイコンも、同じソースから
  • 独自言語の開発は、プログラマの夢・・・

「Onsa」という名前

音叉

  • 「これに合わせる」ための存在
  • DSP 開発のベースとなるもの
  • 基準となる音程を鳴らす道具

音鎖

  • 音の流れをチェインする
  • データフロー形式で、音の処理をつないでいく(音の連鎖)

Onsa の文法

  • 汎用言語の部分は Rust に似ている
    • 関数・構造体・型注釈・所有権の考え方 (ただしライフサイクル管理はない)
  • 信号処理の部分は Lustre に似た同期データフロー
    • flow の本体は「1 サンプルごとに評価される関数」
    • 状態は遅延(prev~)にしか現れず、結線の誤りはコンパイル時に落ちる
  • FAUST と違って、すべての信号に名前があり、信号の更新レートが明確
  • LLM が読みやすい文法を目指した結果、人にも読みやすくなった

FAUST との比較(1次ローパス)

  • FAUST は point-free: 信号に名前がなく、: と ~ で配線をつなぐ。~ が暗黙に 1 サンプル遅らせる
  • Onsa は信号 x・p・y に名前がある。帰還は prev~(^y) と書き手が明示する
  • at block / at sample で、その値がどの速さで変わるかが読める

Rust との比較(汎用の処理)

  • 見た目はほぼ同じ: fn・struct・impl・型注釈、最後の式が値
  • 参照(&mut)の代わりに inout。呼ぶ側にも ! が付き、何が変わるかが 1 行で分かる
  • シグネチャは完全注釈、型推論は関数の中だけ。エラーが局所的で LLM が直しやすい

flow をつなぐ(音鎖)

  • 名前~(...) は、状態を持つ flow のインスタンスを作る
  • 上から下へ、音の流れがそのまま読める
  • ここから C のコードが生成され、プラグインにもマイコンにも入る(予定)

開発の状況

  • 最初に C トランスパイラまで一気に作った
    • 仕様 → 構文解析 → 意味解析 → C 出力、までは動いた
    • でもバグだらけだった・・・
  • 設計をガッチリ固めて、作り直し中
    • 仕様書を先に書き、仕様の例をそのままテストにする
    • 「決めていないことは実装しない」
  • 作り直しの現在地
    • 構文解析(+ フォーマッタ)がほぼ完了
    • これから意味解析(名前・型・レートの検査)へ
