# 提案依存は採用可、防御はインストール経路で固める

DETAILED_SPEC.md 2.2 のコア構成(Node.js 24 + 型ストリップ、markdown-it 15 + markdown-it-container + markdown-it-attrs、Shiki 4、yaml 2)は、**そのまま採用してよい**。2026-10-14 の実測では、コア一式は **56パッケージ・27MB**、`npm audit` の脆弱性は **0件**、インストールスクリプトを持つパッケージも **0件** で、全パッケージのレジストリ署名を検証できた。2025〜2026年の主要なnpmサプライチェーン攻撃の被害リストにも、1つも載っていない。既知のCVEはほぼすべて「攻撃者が細工した入力」を前提にしたDoSなので、作者本人のMarkdownだけを手元でビルドするこのツールには、実害がほとんどない。変えるべきはフロントマター処理で、gray-matter は**不採用**とし、`yaml` で直接パースする(理由は `---js` で `eval` を実行するエンジンを既定で持つこと、2021年から更新が止まっていること、修正版のない勧告が残ること)。オプションの判定は、KaTeX は採用可、sharp は自動縮小(Q17)を採るときだけ条件付き、CodeMirror 6 は当面見送り、BMP変換は jimp を避けて自前実装か bmp-ts + pngjs、または要件から外す、とする。本当のリスクはCVEではない。一つは、依存の大半が少数の個人アカウント(markdown-it 系は vitaly、Shiki 配下の26パッケージは wooorm、CodeMirror は marijn)から provenance なしで公開されている構造。もう一つは、近年のワームが開発者のMac上でインストール時にコードを実行して認証情報を盗む手口である。したがって次の4点を、採用の前提条件として最初のコミットから入れておくべきだ:`ignore-scripts=true` と `min-release-age=7` を書いた `.npmrc`、ロックファイル + `npm ci`、完全一致のバージョン固定、markdown-it の安全側の設定。

## コア構成は56パッケージ・既知脆弱性0件で、そのまま採用できる

実測は、空のディレクトリに `npm install --ignore-scripts` で入れて行った(macOS arm64、Node v25.9.0、npm 11.12.1)。Node 24 そのものでの計測ではないが、純JSのパッケージなので解決結果はほぼ変わらないと見てよい。対象はコア6パッケージ(markdown-it 15.0.2、markdown-it-container 4.0.0、markdown-it-attrs 5.0.1、markdown-it-front-matter 0.2.4、shiki 4.5.0、yaml 2.9.1)。結果は**合計56パッケージ・27MB**、`npm audit` は info から critical まで**すべて0**、preinstall/install/postinstall の宣言と root の `binding.gyp` も**ゼロ**だった。`npm audit signatures` では **56/56 のレジストリ署名を検証できた**([実測ログ m-core](file:///private/tmp/claude-501/-Users-centrevillage-projects-cv-slides/64718e7a-471c-4fae-b948-15f74f53455e/scratchpad/depaudit/m-core/_report.txt))。ただし中身は偏っていて、**Shiki だけで45パッケージ・約22MB(パッケージ数の80%、容量の83%)**を占める。markdown-it + プラグイン + yaml の部分は約11パッケージ・約5MBにすぎない。また、コアのツリーには公開から7日未満の版が1つもなかった。`--min-release-age=7` を付けて解決し直しても、**まったく同じ56パッケージ**になった([実測ログ age7-core](file:///private/tmp/claude-501/-Users-centrevillage-projects-cv-slides/64718e7a-471c-4fae-b948-15f74f53455e/scratchpad/depaudit/age7-core/_tree_age7.txt))。つまり、後述の待機期間ポリシーは今日の時点でコストゼロで導入できる。

ライブラリごとの判定は次のとおり。

代替候補と比べても、この組み合わせは妥当である。marked は依存ゼロの1パッケージで trusted publishing も使っているが、2026-04 に Tokenizer の無限再帰による OOM DoS(CVE-2026-41680)を出している([GHSA-6v9c-7cg6-27q7](https://github.com/advisories/GHSA-6v9c-7cg6-27q7))。unified/remark 系は合計で約63パッケージになる。しかも micromark が `debug ^4.0.0` に依存していて、2025-09-08 に乗っ取られた debug@4.4.2 はその範囲に入っていた([registry: micromark](https://registry.npmjs.org/micromark)、[OSV MAL-2025-46974](https://osv.dev/vulnerability/MAL-2025-46974))。highlight.js と Prism は依存ゼロの1パッケージでサプライチェーン面では軽いが、TextMate 文法を読めない。独自言語(Q22)を JS の DSL で書き直す必要があり、文法の読み込みが「データのパース」から「コードの実行」に変わる。Prism v1 はセキュリティ修正の PR しか受け付けない凍結状態でもある([PrismJS README](https://github.com/PrismJS/prism/blob/master/README.md))。Shiki の45パッケージは、VS Code と同じ文法をそのまま使える忠実度の代償として受け入れられる範囲である。

## 既知CVEは細工入力前提のDoSばかりで、自作スライドには届かない

markdown-it 本体の勧告は5件で、**すべてがDoS(ReDoS か二次計算量)**である。XSS もプロトタイプ汚染も1件もない。2026年は2月・6月・9月に出たが、どれも特定のオプションに限定されている。2月の CVE-2026-2327 と9月の GHSA-253c-mchw-3w2r は `linkify: true` が前提で、後者の PoC では約273KBの入力に89秒かかったが、`linkify: false` なら同じ入力が25〜131msで終わる([GHSA-253c-mchw-3w2r](https://github.com/advisories/GHSA-253c-mchw-3w2r))。6月の CVE-2026-48988 は `typographer: true` の smartquotes ルールで起きる([GHSA-6v5v-wf23-fmfq](https://github.com/advisories/GHSA-6v5v-wf23-fmfq))。依存の linkify-it には High(CVSS 7.5)の2件(CVE-2026-48801、CVE-2026-59887)があるが、これも linkify 経由でしか届かず、解決される 6.1.0 では修正済みだ([GHSA-22p9-wv53-3rq4](https://github.com/advisories/GHSA-22p9-wv53-3rq4))。markdown-it の既定値は `html: false`、`linkify: false`、`typographer: false` である。`validateLink` も `javascript:`、`vbscript:`、`file:`、`data:`(gif/png/jpeg/webp の画像を除く)を拒否する([markdown-it src/markdownit.ts](https://github.com/markdown-it/markdown-it/blob/master/src/markdownit.ts))。linkify と typographer はスライドに不要なので無効のままにし、15.0.2 以上に固定すれば、既知の経路はすべて塞がる。15.0.0 では内部の subpath exports(`markdown-it/lib/*`)が削除された([CHANGELOG](https://github.com/markdown-it/markdown-it/blob/master/CHANGELOG.md))。独自プラグインは `md.block.ruler` などの公開APIだけで書くこと。

仕様の「生HTMLはサニタイズしない」(`html: true`)は、脅威モデルの範囲内なら問題ない。入力が作者本人のファイルに限られる以上、raw HTML を通しても「自分で書いたスクリプトが動く」以上のことは起きないからだ。公式の安全ガイドは、HTML を有効にするなら外部サニタイザを併用する戦略を示している([markdown-it docs/safety.md](https://github.com/markdown-it/markdown-it/blob/master/docs/safety.md))。サニタイザを省けるのは、入力を完全に信頼できる今の前提があるからである。注意すべきは markdown-it-attrs のほうだ。`allowedAttributes` の既定値は `[]` で、これは**全属性を許可**するという意味になる。README 自身も `![](img.png){onload=fetch(...)}` のような属性注入を例に挙げ、allowlist の使用を勧めている([markdown-it-attrs README](https://github.com/arve0/markdown-it-attrs/blob/master/README.md))。仕様で属性記法を使うのは画像の `{width=60%}` だけなので、`allowedAttributes: ['width']` に絞れば、機能は何も失わずに将来の事故を防げる。将来、他人のスライドやWebからコピーしたMarkdownを変換するようになったら、それは信頼境界の外の入力になる。そのときは `html: false` に戻すか、サニタイザを入れる必要がある。

`yaml` の勧告は2件で、どちらも細工されたYAMLによるDoSである。CVE-2023-2251 は 2.2.2 で、CVE-2026-33532 は 2.8.3 で修正済み([OSV GHSA-f9xv-q969-pqx4](https://osv.dev/vulnerability/GHSA-f9xv-q969-pqx4)、[GHSA-48c2-rrv3-qjmp](https://github.com/eemeli/yaml/security/advisories/GHSA-48c2-rrv3-qjmp))。後者には実装上の教訓がある。`[` を5,000個入れ子にするような入力では、`YAMLParseError` ではなく **`RangeError` が投げられる**。仕様は「フロントマターのYAMLが不正なら終了コード1」としているので、`YAMLParseError` だけを捕捉するのではなく、`Error` 全般を捕捉してエラー扱いにすべきだ。対照的に js-yaml は、2025年11月にプロトタイプ汚染(CVE-2025-64718)を出し、2026年6〜9月にCPU DoSの勧告を約8件出している([GHSA-mh29-5h37-fv8m](https://github.com/nodeca/js-yaml/security/advisories/GHSA-mh29-5h37-fv8m)、[GHSA-2883-xcg3-v3hh](https://github.com/nodeca/js-yaml/security/advisories/GHSA-2883-xcg3-v3hh))。仕様が `yaml` を選んだのは正しい。

Shiki については、shiki 本体、`@shikijs/*`、vscode-textmate、oniguruma-to-es、hast-util-to-html のどれにも、OSV/GHSA の勧告が**0件**だった([OSV.dev](https://osv.dev/list?ecosystem=npm&q=shiki))。ツリー内で唯一勧告が出た mdast-util-to-hast(CVE-2025-66400)も、解決される 13.2.1 で修正済みである([GHSA-4fh9-h7wg-q85m](https://github.com/advisories/GHSA-4fh9-h7wg-q85m))。独自の TextMate 文法は `JSON.parse` で読めば「データ」であり、コード実行の経路はない。最悪のケースは、壊れた正規表現によるビルドのハング(ReDoS)である。気をつけたいのは、`tokenizeTimeLimit`(既定500ms)の判定が正規表現スキャンの「合間」にしか行われない点だ。そのため、1回の破滅的なバックトラッキングは止められない([vscode-textmate tokenizeString.ts](https://github.com/microsoft/vscode-textmate/blob/main/src/grammar/tokenizeString.ts))。エンジン選択はトレードオフになる。Oniguruma WASM エンジンには1マッチあたり1,000万回のリトライ上限があり、WASM のサンドボックス内で動く。一方で、上流の Oniguruma は **2025-04-24 にプロジェクト終了を宣言してアーカイブ**されており([GitHub: kkos/oniguruma](https://github.com/kkos/oniguruma))、Shiki が内包する vscode-oniguruma も 2023-09 以降リリースがない。JS エンジン(oniguruma-to-es)は活発に保守されている。ただし V8 のバックトラッキングにはステップ上限がない。既定では変換できないパターンに出会うと例外を投げる(strict)ので、自作文法の非互換に早く気付ける([Shiki docs: RegExp Engines](https://shiki.style/guide/regex-engines))。安全面の差は小さいので、長期保守を優先して **JS エンジンを第一候補**とし、自作文法が変換できない場合だけ Oniguruma に切り替えるのがよい。

Node.js 24 は 2026-10-20 に Maintenance LTS へ移行する。それでも **2028-04-30 までセキュリティ修正が続く**([nodejs/release](https://github.com/nodejs/release))。2025〜2026年の 24.x 向けセキュリティ修正は、HTTP/2、TLS、WebCrypto のDoS・認証の問題が中心で、オフラインでファイルを変換するだけのCLIにはほとんど関係しない。直近の修正版は 2026-07-29 の **24.18.1** である([Node.js July 2026 security releases](https://nodejs.org/en/blog/vulnerability/july-2026-security-releases))。型ストリップは **v24.12.0 で Stable** になった。確認した6回分のセキュリティリリースのどれにも、型ストリップは登場しない([Node.js v24 TypeScript docs](https://nodejs.org/docs/latest-v24.x/api/typescript.html))。型ストリップの「リスク」は振る舞いに関するもので、型チェックは一切行われず、`tsconfig.json` も無視される。このため、フロントマターの型は実行時に明示的に検証しなければならない。また、`enum` などのように消去できない構文はエラーになる。開発時には `tsc --noEmit` を `erasableSyntaxOnly` 付きで回すのが公式の推奨である。逆に、tsx・ts-node・esbuild といった実行時トランスパイラが不要になるので、依存ツリーが小さくなるという利点がある。

## 弱点は少数の個人アカウントと、開発機で走るインストール時コード

2025〜2026年のnpm攻撃は、単発のメンテナ乗っ取りから、自己増殖するワームへと進化した。2025-09-08 には、TOTP まで入力させるフィッシングで chalk/debug など18パッケージ(合計で週20億ダウンロード超)が乗っ取られた([Aikido](https://www.aikido.dev/blog/npm-debug-and-chalk-packages-compromised))。同年11月の Shai-Hulud 2.0 は、`preinstall` から Bun を起動して認証情報を盗み、約700〜800パッケージと25,000超のリポジトリに広がった([Wiz](https://www.wiz.io/blog/shai-hulud-2-0-ongoing-supply-chain-attack))。2026年には axios(3月)、TanStack(5月、169パッケージ・373版)、@antv、Red Hat、AsyncAPI と続き、8月の ChainDrop は数百パッケージに達した([CISA](https://www.cisa.gov/news-events/alerts/2026/04/20/supply-chain-compromise-impacts-axios-node-package-manager)、[Unit 42](https://unit42.paloaltonetworks.com/monitoring-npm-supply-chain-attacks/))。特にこのプロジェクトに関係するのは、2つの手口である。2025年8月の s1ngularity は、ローカルの AI CLI(Claude、Gemini、Amazon Q)を**権限確認を省くフラグ付きで起動**し、ファイルシステムを探索させた([Wiz](https://www.wiz.io/blog/s1ngularity-supply-chain-attack))。ChainDrop は、リポジトリに **VS Code と Claude のフックを仕込み**、プロジェクトを開くたびにローダーが再実行されるようにした([Datadog Security Labs](https://securitylabs.datadoghq.com/articles/npm-worm-compromises-popular-npm-packages/))。狙われるのは生成されたHTMLではない。SSH鍵、`~/.npmrc`、GitHub の認証情報、AIエージェントの設定が置かれた**作者のMacそのもの**である。

提案したライブラリが、これらの事件に巻き込まれた形跡はない。OSV の悪性パッケージ記録(MAL-*)は、debug、chalk、keyv、axios といった既知の被害パッケージでは正しくヒットした。しかし yaml、sharp、katex、CodeMirror/Lezer、markdown-it 系、それぞれの依存では0件だった([OSV MAL-2026-11524](https://osv.dev/vulnerability/MAL-2026-11524))。Shai-Hulud 2.0 の IOC 一覧(Wiz と Datadog、各795行)を Shiki の45パッケージと突き合わせた結果も、**重複ゼロ**だった([Wiz IOC list](https://github.com/wiz-sec-public/wiz-research-iocs/blob/main/reports/shai-hulud-2-packages.csv))。「markdown-it」を名前に含む感染例は、無関係なサードパーティ製の `@accordproject/markdown-it-cicero` だけである([GitLab Advisory](https://advisories.gitlab.com/pkg/npm/@accordproject/markdown-it-cicero/))。ただし、ChainDrop と、2026年10月にも続いている後続波([The Hacker News](https://thehackernews.com/2026/10/tensorlake-npm-package-compromised-to.html))については、完全な IOC 一覧を照合できていない。したがって、「被害記録がない」は「安全の証明」ではない。

構造的な弱点は、公開アカウントの集中にある。実測では、コアの56パッケージは**18の npm アカウント**で管理されていた。そのうち wooorm 1人が **26パッケージ**(Shiki 配下の unified/hast/micromark 系)を公開し、vitaly 1人が markdown-it、markdown-it-container、linkify-it、mdurl、uc.micro、argparse の6つを公開している([registry: markdown-it](https://registry.npmjs.org/markdown-it))。CodeMirror に至っては、18パッケージ**すべて**が marijn 1人のアカウントから出ている。リポジトリの多くも自前のフォージ `code.haverbeke.berlin` に移っている([registry: @codemirror/view](https://registry.npmjs.org/@codemirror/view))。ビルド元を証明する provenance 付きで公開されているのは、コア56パッケージのうち **9つ(Shiki の8パッケージと entities)だけ**だった。とはいえ、provenance はもう安全の目安にならない。TanStack、Red Hat、ChainDrop の悪性版は、どれも**正規の SLSA provenance 付き**で公開された([Unit 42](https://unit42.paloaltonetworks.com/monitoring-npm-supply-chain-attacks/))。2026年10月には、trusted publishing がリポジトリを ID ではなく名前で照合していた欠陥「SlugFest」も公表され、1,500超のパッケージがその影響を受ける状態だった([Help Net Security](https://www.helpnetsecurity.com/2026/10/13/slugfest-npm-trusted-publishing-flaw/))。採否の判断で重視すべきなのは、provenance の有無よりも、依存の数、インストールスクリプトの有無、ロックファイルの運用である。

インストールスクリプトを止めるだけでは足りない理由もある。chalk/debug の悪性版はインストールスクリプトを使わず、**モジュールが読み込まれたときに動く**ペイロードだった([Aikido](https://www.aikido.dev/blog/npm-debug-and-chalk-packages-compromised))。ビルド時にしか動かない markdown-it、Shiki、yaml でも、ビルドのたびに作者の権限で実行されることに変わりはない。CodeMirror のように出力HTMLへ同梱するものは、さらに聴衆のブラウザにまで届く。この種のペイロードに効くのは、新しい版をすぐに入れない「待機期間」である。悪性版の多くは数時間で削除されたが、Shai-Hulud 2.0 では**検知から3日後もまだ約15版が npm に残っていた**([Wiz](https://www.wiz.io/blog/shai-hulud-2-0-ongoing-supply-chain-attack))。待機期間は1日ではなく7日にする根拠がここにある。

## オプションは KaTeX だけ即採用、sharp・CodeMirror・BMP は条件付き

**KaTeX** は採用してよい。0.19.0(2026-10-01)の依存は CLI 用の commander だけで、計2パッケージ・約4.6MBである。勧告は6件ある。2024年3月の4件(0.16.10 で修正)、2025年1月の `\htmlData`(CVE-2025-23207、0.16.21 で修正)、2026年10月の「別の箇所でのプロトタイプ汚染があると `trust` が反転する」問題(CVE-2026-103923、0.18.2 で修正)である。どれも、`trust` を有効にした場合か、信頼できない数式を描画した場合にしか効かない([GHSA-238p-pmpm-9mq7](https://github.com/KaTeX/KaTeX/security/advisories/GHSA-238p-pmpm-9mq7)、[GHSA-cg87-wmx4-v546](https://github.com/KaTeX/KaTeX/security/advisories/GHSA-cg87-wmx4-v546))。`trust: false`(既定値)のままにし、`maxSize` を有限の値(例: 10)にする。出力は Q14 の推奨どおり `output: 'mathml'` にすれば、CSS とフォントの埋め込みも不要になる([KaTeX options](https://katex.org/docs/options))。注意点として、KaTeX は provenance なしの個人公開で、2026-08-31〜10-01 の1か月に8回リリースしている。待機期間ポリシーが効いてくるのはこういうパッケージだ。

**sharp** は、Q17(大きな画像の自動縮小)を採用する場合だけ入れる。インストール時のリスクはほぼ消えている。0.35.0 以降はライフサイクルスクリプトがなく、ビルド済みバイナリはプラットフォーム別の optionalDependencies として届く。trusted publishing と SLSA provenance も付いている([registry: sharp](https://registry.npmjs.org/sharp))。問題は実行時で、libvips 8.18.7 と一緒に、rsvg、heif、tiff、xml2、cairo/pango など27個のネイティブライブラリが同梱されている([実測 versions.json](file:///private/tmp/claude-501/-Users-centrevillage-projects-cv-slides/64718e7a-471c-4fae-b948-15f74f53455e/scratchpad/depaudit/o-sharp/node_modules/@img/sharp-libvips-darwin-arm64/versions.json))。2026年だけでも、libvips の4件(うち2件が High、0.35.0 で修正)、libheif 由来で「RCE の可能性」があるもの(0.35.4 で修正)、librsvg CVE-2026-96889 由来で同じく RCE の可能性があるもの(0.35.5 で修正)が出ている([GHSA-rgj7-g3m4-5g8c](https://github.com/lovell/sharp/security/advisories/GHSA-rgj7-g3m4-5g8c)、[GHSA-wq5f-xc86-pv6w](https://github.com/lovell/sharp/security/advisories/GHSA-wq5f-xc86-pv6w))。いずれも「信頼できない画像を処理する場合」に限られ、自分で撮った JPEG/PNG なら実害は小さい。ただ、Webから拾った画像を混ぜるなら話は別だ。sharp は修正版バイナリを先に出し、GHSA は数日〜2か月遅れて公開される。勧告ではなくリリースを追うほうが早い。採用するなら、0.35.5 以上に固定し、`sharp.block()` で SVG・HEIF・TIFF・GIF・VIPS のローダーを止めて、sharp には JPEG/PNG/WebP だけを渡す。SVG と GIF はデコードせず、そのまま埋め込めばよい。なお、npm 11.12.1 は不要な `@img/sharp-wasm32` などの3パッケージ(9.7MB、管理アカウント9つ分)も余分に入れてしまった。実際に必要なのは6パッケージ・約19MBである([実測ログ o-sharp](file:///private/tmp/claude-501/-Users-centrevillage-projects-cv-slides/64718e7a-471c-4fae-b948-15f74f53455e/scratchpad/depaudit/o-sharp/_report.txt))。自動縮小を諦めて、作者が事前に縮小する運用(macOS なら標準の `sips` など)にすれば、ネイティブコードは一切不要になる。

**CodeMirror 6** は、Q40 の推奨どおり「表示のみ」で始め、当面は入れない。勧告は6年間0件で、v5 の CVE-2020-7760 があるだけだ([OSV GHSA-4gw3-8f77-f72c](https://osv.dev/vulnerability/GHSA-4gw3-8f77-f72c))。サードパーティ依存もゼロである。ただし前述のとおり、18パッケージすべてが1つの個人アカウントに依存している。しかも、他のライブラリと違って**出力HTMLに同梱されて聴衆のブラウザで動く**。実測では、このツリーで4つのパッケージが公開から7日未満で、その中には 2026-10-07 に作られたばかりの新パッケージ `@codemirror/streamparser` も含まれていた。`min-release-age=7` で解決し直すと、これらは1つ前の版に戻り、新パッケージも外れた([実測ログ age7-codemirror](file:///private/tmp/claude-501/-Users-centrevillage-projects-cv-slides/64718e7a-471c-4fae-b948-15f74f53455e/scratchpad/depaudit/age7-codemirror/_tree_age7.txt))。待機期間ポリシーが実際に働いた例である。将来 Q40 を C にする場合は、固定した版を一度だけバンドルしてリポジトリ(例: `scripts/runtime/vendor/`)にコミットし、更新は意図したときだけ行う方式を勧める。そうすれば、レジストリが後で侵害されても、生成済みのスライドには届かない。公式例でも、バンドル後のサイズは約400KB(gzip で135KB)である([CodeMirror: Bundling](https://codemirror.net/examples/bundle/))。

**BMP変換** には注意点がある。そもそも sharp のビルド済みバイナリは BMP を入力形式として**サポートしていない**([sharp install docs](https://sharp.pixelplumbing.com/install))。jimp 1.6.1 なら変換できるが、約63パッケージを引き込む。その中には2025年に乗っ取られた debug、2026年にDoS CVEを2件出した file-type、プロトタイプ汚染の CVE-2023-0842 を持つ xml2js が含まれる([OSV MAL-2025-46974](https://osv.dev/vulnerability/MAL-2025-46974)、[OSV file-type](https://osv.dev/list?ecosystem=npm&q=file-type))。BMPを1枚変換するためだけには重すぎる。bmp-js は2018年から更新がないので避ける。現実的な選択肢は3つで、優先順に次のとおり。第一に、Q18 で「使う予定がない」と答えて要件から外す。第二に、無圧縮BMP(24/32bit)のデコーダを約100行で自作する。第三に、依存ゼロの **bmp-ts 1.0.9 + pngjs 7.0.0**(どちらも勧告0、ただし2023〜2024年から休眠)を使う([registry: bmp-ts](https://registry.npmjs.org/bmp-ts)、[registry: pngjs](https://registry.npmjs.org/pngjs))。sharp を採用済みなら、bmp-ts でデコードした RGBA を sharp の PNG エンコーダに渡せば、pngjs も不要になる。

## 最初のコミットで入れる設定: .npmrc 5行とライブラリ設定

最も効果が大きいのは、リポジトリ直下の `.npmrc` である。CISA は axios 事件のアラートで、まさに `ignore-scripts=true` と `min-release-age=7` を推奨している([CISA](https://www.cisa.gov/news-events/alerts/2026/04/20/supply-chain-compromise-impacts-axios-node-package-manager))。実測では、sharp を含むどのツリーでもインストールスクリプトは不要だったので、`ignore-scripts=true` で失う機能はない。npm の ini パーサが行末コメントをどう扱うかは確認していないので、コメントは必ず独立した行に書く。

```ini
# 依存パッケージのインストールスクリプトを一切実行しない(実測で必要なものはゼロ)
ignore-scripts=true
# 公開から7日未満の版を解決しない(npm 11.10.0 以上)
min-release-age=7
# git 依存と tarball URL 依存を禁止(npm 12 では既定値。allow-remote は npm 11.15.0 以上)
allow-git=none
allow-remote=none
# package.json に ^ を付けず、完全一致で記録する
save-exact=true
```

npm のバージョンには注意が要る。`min-release-age` は **npm 11.10.0**(2026-02-11)で追加された設定なので、それより古い npm は単に無視する([npm CLI CHANGELOG](https://raw.githubusercontent.com/npm/cli/latest/CHANGELOG.md))。Node 24 に同梱される npm の版は今回確認できていない。`npm -v` で 11.10 以上かを必ず確かめること。npm 12(2026-07-08)は、依存のライフサイクルスクリプトを既定で遮断するようになり、Node 24 では 24.15.0 以上を要求する。また、**未知の `.npmrc` キーをエラーとして扱う**ようになったので、上の5行以外のキーは書かないほうがよい([npm CLI v12.0.0](https://api.github.com/repos/npm/cli/releases/tags/v12.0.0))。npm 12 を使うなら、`ignore-scripts` の代わりに既定の遮断と `strict-allow-scripts=true` を組み合わせる手もある。この組み合わせなら、依存が新たにインストールスクリプトを持ち込んだ瞬間にインストールがエラーになり、ワームの典型的な兆候にすぐ気付ける([npm v12 config](https://docs.npmjs.com/cli/v12/using-npm/config))。他のプロジェクトも守りたいなら、`npm config set min-release-age 7 --location=user` でユーザー全体にも設定できる([Classmethod](https://dev.classmethod.jp/articles/npm-min-release-age-setup/))。

運用面では、`package.json` の依存を完全一致で書く(例: `"markdown-it": "15.0.2"`、`"markdown-it-attrs": "5.0.1"`、`"markdown-it-container": "4.0.0"`、`"shiki": "4.5.0"`、`"yaml": "2.9.1"`)。`"engines": { "node": ">=24.18.1" }` を宣言し、`package-lock.json` はコミットする。クリーンな環境では必ず `npm ci` で入れる。TypeScript は型チェック専用の devDependency(5.8 以上)にとどめる。更新は自動化せず、月1回程度の手作業で十分だ。`npm outdated` で候補を見て、待機期間が効いた状態で更新する。ロックファイルの差分で、新しく増えたパッケージ名、`hasInstallScript`、公開者の変化を読み、`npm audit` と `npm audit signatures` を流してからコミットする。2026年のワームはリポジトリ内にフックを仕込むので、依存を更新した後は `.claude/`、`.vscode/`、`.github/workflows/` の差分も確認する。AIエージェントに `npm install` を実行させるときは、権限確認を省くモードを使わない。GitHub で管理していて Dependabot を使うなら、`cooldown: { default-days: 7 }` で同じ待機期間を揃えられる。ただし、cooldown はセキュリティ更新には効かない([Dependabot options reference](https://docs.github.com/en/code-security/dependabot/working-with-dependabot/dependabot-options-reference))。

ライブラリ側の設定は次のとおりにする。

| 対象 | 設定値 | 理由 |
|---|---|---|
| markdown-it | `html: true`、`linkify: false`、`typographer: false` | 生HTMLは仕様どおり許可する。既知のDoSはすべて linkify と typographer の経路 |
| markdown-it-attrs | `allowedAttributes: ['width']` | 既定の `[]` は全属性許可。仕様で使うのは `{width=...}` だけ |
| 独自プラグイン | 公開API(`md.block.ruler` など)だけを使う | 15.0.0 で内部の subpath exports が削除された |
| フロントマター | parse.ts で先頭の `---` を切り出して `yaml.parse`。例外は `Error` 全般を捕捉して終了コード1 | CVE-2026-33532 は `RangeError` を投げる。gray-matter は使わない |
| Shiki | JS 正規表現エンジン(`createJavaScriptRegexEngine`)、`tokenizeMaxLineLength` に上限(例: 1000)、文法は `JSON.parse` で読み込む | 上流 Oniguruma は終了済み。文法を JS モジュールとして `import` するとコード実行になる |
| KaTeX | `trust: false`、`output: 'mathml'`、`maxSize: 10` | XSS 系の勧告はすべて trust 有効が前提。MathML ならフォントの埋め込みが不要 |
| sharp(採用時) | `sharp.block({ operation: ["VipsForeignLoadSvg", "VipsForeignLoadHeif", "VipsForeignLoadTiff", "VipsForeignLoadNsgif", "VipsForeignLoadVips"] })` | 2026年の勧告に出たデコーダをすべて止める |
| Node / TypeScript | 24.18.1 以上。tsconfig に `noEmit`、`erasableSyntaxOnly`、`verbatimModuleSyntax`、`rewriteRelativeImportExtensions` | 型ストリップは型チェックも消去不能構文の変換もしない |

実行時のサンドボックスは、補助的な扱いにとどめる。Node 24 のパーミッションモデル(`--permission --allow-fs-read=… --allow-fs-write=…`)は Stable になっている。しかし、Node 24 には**ネットワークを制限するフラグがない**。公式ドキュメントも「悪意あるコードからは守らない」と明言している。2026年には、High 2件(CVE-2025-55130、CVE-2026-58043)を含む迂回CVEも出た([Node v24 permissions docs](https://nodejs.org/docs/latest-v24.x/api/permissions.html)、[Node July 2026 security releases](https://nodejs.org/en/blog/vulnerability/july-2026-security-releases))。`gen_slide.sh` に足すなら「シートベルト」程度の位置づけで、まず `--permission-audit` で必要なパスを洗い出してからにすること。実行時にネットワークまで本当に遮断できるのは Deno の権限モデルだけである。ただし、sharp のようなネイティブアドオンを使うと `--allow-ffi` が必要になり、その時点で効果がなくなる([Deno security docs](https://docs.deno.com/runtime/fundamentals/security/))。Q04 を覆すほどの理由にはならない。

## 結論

このプロジェクトの判断基準は、「CVEが何件あるか」から「コードがどの経路で手元に届くか」へ移すべきだ。調べたライブラリの勧告は、ほぼすべて細工された入力によるDoSで、作者本人の入力しか扱わないビルドツールにはほとんど関係しない。対して2025〜2026年の実害は、インストール時やモジュール読み込み時に開発機で走るコードと、正規の provenance を付けて公開された悪性版から生じている。そのため、`.npmrc` の5行、ロックファイル + `npm ci`、7日の待機期間は、どのライブラリを選ぶかよりも効く。しかも実測では、コア構成でのコストはゼロだった。待機期間を入れても解決結果は1パッケージも変わらず、インストールスクリプトを止めても失う機能はない。

もう一つの示唆は、QUESTIONS.md の回答そのものがセキュリティ判断になっているということだ。KaTeX(Q14)で増えるのは2パッケージだけである。一方、自動縮小(Q17)は libvips と27個のネイティブライブラリを、BMP変換(Q18)は選び方次第で63パッケージを、本格エディタ(Q40)は聴衆のブラウザで動く1アカウント依存の18パッケージを持ち込む。機能の要否を答えるときにこのコストを並べて考えれば、攻撃面は最小のまま保てる。残る不確実性は3点ある。Node 24 同梱の npm の版、ChainDrop 以降の完全な IOC 一覧との照合、各メンテナの2FA状況で、どれも公開情報では確認できなかった。だからこそ、特定のライブラリへの信頼ではなく、取り込みの手順で守る設計にしておく価値がある。
